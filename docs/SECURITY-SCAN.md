# Security scan record

Run on 2026-11-03 against commit `a1972b9` on Windows. Nothing here is a claim
that the code has no bugs; it is a record of what was executed and what it said.

## Tools

| Tool | Version | How installed |
| --- | --- | --- |
| gitleaks | 8.30.1 | release zip from GitHub, run from a temp directory (not a project dependency) |
| semgrep | 1.183.0 | `pip install semgrep` (OSS rules) |
| trivy | 0.76.1 | release zip from GitHub |

None of them is committed to the repo or added to `package.json`: they are
dev-machine tools, and a pinned scanner in `devDependencies` would ship its own
dependency tree into every install. CI runs gitleaks already
(`.github/workflows/ci.yml`, `secrets` job, full history).

## Gitleaks

```bash
gitleaks git . --redact          # 144 commits, 13.45 MB, 1.01s
```

**Result: `no leaks found`, exit 0.** Full history, not just the working tree,
so a credential that was committed and later deleted would still show up.

```bash
gitleaks dir . --redact          # 102.71 MB, 2.72s
```

**Result: 3 findings, exit 1.** All three are correct detections of real secrets
in files that are deliberately untracked:

| File | Rule | Verdict |
| --- | --- | --- |
| `.env.local` | generic-api-key | Supabase anon key. Gitignored (`.gitignore:31`, `.env.*`). Never committed: `git log --all -- .env.local` is empty. |
| `.env.local` | jwt | Same key, matched by the JWT rule. |
| `tests/.auth/state.json` | jwt | Playwright session for the test account. Gitignored (`.gitignore:45`). Regenerated by `tests/auth.setup.ts`. |

The distinction matters: `git` mode is the gate (what leaked), `dir` mode is an
inventory. A clean `dir` scan on a developer machine with a working `.env.local`
would mean the scan is not looking.

## Semgrep

```bash
semgrep scan --config p/typescript --config p/react --config p/owasp-top-ten \
  --config p/secrets --exclude node_modules --exclude dist --exclude release \
  --exclude android --exclude ios
```

290 rules, 540 files, ~99.9% of lines parsed. **17 findings, all reviewed:**

| Count | Rule | Where | Verdict |
| --- | --- | --- | --- |
| 14 | `github-actions-mutable-action-tag` | the three workflows | **Accepted.** Steps use `@v4` / `@v2` rather than a commit SHA, so a repointed tag could change what runs. Real risk is low here: the repo has no forks with secrets, `permissions: contents: read` is set at workflow level, and the only secret is `GITHUB_TOKEN`. Fix is to pin every action to a full SHA and let Dependabot bump it; deferred because it makes the workflows unreadable for a solo maintainer. Recorded, not hidden. |
| 3 | `wildcard-postmessage-configuration` | `.opencode/skills/impeccable/scripts/live-browser.js` | **Not our code.** A vendored design skill's dev script, never imported by the app, not in `dist`, not in `app.asar`. Excluded from the shipped bundle (see the packager whitelist in `electron/main.js`'s script). |

Zero findings in `src/`, `electron/`, `supabase/` or `tests/`. In particular no
`dangerouslySetInnerHTML` with unsanitised input, no `eval`, no SQL string
concatenation (there is no server-side SQL: data access is PostgREST plus
`SECURITY DEFINER` functions whose arguments are bound, not interpolated).

## Trivy

```bash
trivy fs . --scanners vuln,secret,misconfig --severity CRITICAL,HIGH \
  --skip-dirs node_modules,.git,dist,release,android,ios,test-results,screenshots
```

**Result: 0 vulnerabilities, 0 secrets, 0 misconfigurations, exit 0** across the
two scanned targets (`package-lock.json`, `.env.local`). Trivy's secret scanner
does not flag the Supabase anon key that gitleaks does, because an anon key is
not shaped like a credential it recognises; that is a coverage gap, not a clean
bill of health, which is why gitleaks is the primary tool.

## Dependency audit

```bash
npm audit --omit=dev     # production dependency tree
npm audit                # everything, including build tooling
```

| Scope | Total | Critical | High | Moderate |
| --- | --- | --- | --- | --- |
| Production (`--omit=dev`) | **0** | 0 | 0 | 0 |
| All dependencies | **7** | 0 | 0 | 7 |

The seven are one chain, all in build tooling:

- `@capacitor/cli` → `rimraf` → `glob` → `minimatch`
- `@electron/packager` → `@electron/asar` → `glob` → `minimatch`
- `@electron/packager` → `@electron/universal` → `@electron/asar`

`minimatch` ReDoS via glob-part amplification and a `glob` abort-signal bypass.
Both are denial-of-service in a file walker, reachable only by whoever runs
`npm run desktop:package` or `cap sync`, with the patterns those scripts already
hardcode. None of it is in `dist/`, none of it is in the shipped `.exe` runtime
(the asar contains only `dist/`, `electron/` and `package.json`), and neither
package is reachable from browser code.

The only advertised fix is a breaking downgrade of `@electron/packager` and
`@capacitor/cli` to versions from before the vulnerable `glob`. Downgrading the
tool that produces the release binary to clear a dev-time DoS is the wrong trade,
so it is left and recorded. This will clear itself when upstream publishes a
release on the patched `glob`.

## What these scans cannot tell you

- Nothing about the RLS policies. `scripts/rls-audit.mjs` covers the static half
  (every table has RLS and a policy); the live half is `scripts/tenant-probe.mjs`
  and `scripts/security-probe.mjs`, which need real credentials.
- Nothing about logic errors, authorisation mistakes inside a `SECURITY DEFINER`
  function, or a policy that says `true` where it should say `org_has_role(...)`.
  That is what the SQL test suites in `supabase/tests/` are for.
- Semgrep's `p/owasp-top-ten` on a React SPA mostly checks the client, and the
  client is not where the authorisation decisions live. The database is.
